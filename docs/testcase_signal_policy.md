# Testcase Signal Policy

## 目标

本文件用于固化“高信号 testcase / 低信号 testcase”的统一判定标准，作为后续 `coverage` 分层、`generator` 去重、主用例 / audit 拆分、`fidelity` 强绑定、`traceability` 重建与 `scorer` 门禁的共同依据。

本文件不是展示型说明文档，而是产物分流与评分的口径真源。

## 核心原则

1. 本轮目标不是继续增加 testcase，而是压缩低价值 testcase，提升主用例业务信号密度。
2. 主 testcase 应优先承接业务行为、条件约束、边界异常、状态切换、数据过滤排序和高优 fidelity。
3. 结构性低信号检查不能继续挤占主用例，应转入结构化 audit 链路。
4. 若规则无法稳定落入主用例，应显式进入 audit 或缺失报告，不能靠泛化标题占位。
5. 后续所有分流都必须保留可追踪来源，不能因为“收敛”而丢失 provenance。
6. `context_only` 与 `oracle_only` 只用于背景理解或生成后评分，默认只能进入 audit，不能进入主 testcase。
7. 一条来源规则包含多个可独立失败分支时，应先拆为 `atomic_assertions`，再分别进入 Coverage 与 Case Plan。

## 高信号判定

满足以下任一条件，应优先视为高信号 testcase：

- 直接验证业务核心行为、主流程打通、状态切换或页面核心联动。
- 直接验证条件展示、条件必填、条件只读 / 可编辑、边界值、非法输入。
- 直接验证数据源过滤、排序、候选项选择约束。
- 直接承接高优 `explicit_rules.fidelity_points`。
- 测试步骤或预期结果中需要保留精确时间、数量、状态、归属、排序口径、容器结果等原词约束。
- 一条用例能够稳定回答“这个业务规则有没有被满足”，而不是只回答“字段长得对不对”。

## 低信号判定

满足以下任一条件，应优先视为低信号 testcase：

- 仅检查字段控件类型、默认展示形式、枚举定义是否一致，且不直接影响业务结果。
- 仅检查列表展示元数据，如创建人、创建时间、修改时间等展示属性。
- 仅用“基础属性与控件定义一致”“展示格式正确”这类模板表达，缺少业务结果判定。
- 用例标题、步骤、预期高度模板化，替换字段名后可跨多个页面直接复用。
- 验证目标更适合作为批量结构检查，而不是独立主 testcase。

## 主 testcase 优先承接范围

以下规则类型优先进入主 testcase：

- `required_when`
- `readonly_when`
- `editable_when`
- `value_boundary`
- `invalid_input`
- `data_source_filter`
- `data_source_order`
- 主流程
- 状态切换
- 页面核心行为
- 高优 `fidelity_points`

## 后台配置页通用生成规则

当结构化 PRD 中出现“后台配置页 / 管理页 + 添加弹窗 + 列表管理”的配置实体时，不允许只生成字段校验用例。若配置实体同时具备名称/状态字段，以及展示、跳转、tab、活动、链接、触达用户、展示规则等配置字段，应自动补齐以下主用例：

- 真实新增链路：覆盖点击添加入口、填写核心字段、保存/确认、列表新增与字段回显。
- 真实编辑链路：覆盖点击编辑入口、修改核心字段、保存/确认、原列表记录更新且不新增重复记录。
- 真实删除链路：覆盖点击删除入口、确认删除、列表移除，并验证该配置不再作为前台展示或排序有效数据。
- 容量限制链路：对“单 tab 不超过 N 条 / 每 tab 最多 N 条”类规则，同时生成 B 端保存拦截用例和 C 端展示上限用例。
- 展示频次链路：对“每日首次 / 每次进入 / 仅一次”等频次枚举，不只校验枚举存在，还要生成前台重复进入后的展示频次行为用例。
- 跨字段约束链路：对“前值 <= 后值”等字段间规则，生成非法组合保存失败用例。
- 数据源组合链路：当同一候选字段同时存在过滤和排序规则时，生成“过滤 + 排序同时成立”的组合断言用例。

这些规则是配置页类需求的通用规则，不绑定 PT081 或小程序广告位模块名称。

以下精确约束属于主 testcase 高优保真对象：

- `5s自动轮播`
- `每tab最多5条`
- `每tab最多4条`
- `每tab最多3条`
- `默认关闭`
- `顶部tab归属`

## audit 优先承接范围

以下内容不应默认进入主 testcase：

- 普通字段 `field_property`
- 创建人 / 创建时间 / 修改时间等展示元数据属性
- 列表列头、表头顺序、静态展示属性
- 不直接影响业务结果的候选项展示样式核对

后续进入 Phase 3 时，audit 产物分流遵循以下方向：

- `audit_item`：仍需逐项核查、但不应进入主 testcase 的结构项。
- `group_audit`：适合批量聚合检查的结构项。
- `drop`：低价值且重复度高，不再单独产出。

## grouped audit 固定类型

`grouped_audit` 只允许以下三类：

1. `page_level_metadata_audit`
2. `module_level_field_property_audit`
3. `table_header_audit`

`grouped_audit` 必须保持结构化、可追踪、可评分，不得退化为泛化说明文档。

## 低信号项的优先去向

以下项优先进入 `group_audit` 或 `drop`，而不是独立 `audit_item`：

- `创建人`
- `创建时间`
- `修改时间`
- 列表展示元数据属性

以下项可保留为 `audit_item`，但不进入主 testcase：

- 普通字段基础属性核查
- 普通候选项展示格式核查
- 结构化字段定义一致性核查

## 禁止继续扩张的泛化表达

以下表达不应再作为主 testcase 标题主干：

- `基础属性与控件定义一致`
- `字段矩阵完整性`
- `条件联动正确`
- `页面配置正确`
- `展示格式正确`

如必须保留相关检查，应转入 audit 链路，并补充结构化目标与来源。

## 去重阶段的保护边界

即使标题接近，以下类型在后续 Phase 2 也禁止误合并：

- `data_source_filter` 与 `data_source_order`
- `conditional_visibility` 与 `conditional_required`
- `readonly_when` 与 `editable_when`
- `boundary_valid` 与 `boundary_invalid`
- 高优 `explicit_rule` fidelity 用例 与 普通 `ai_reasoning` 补充用例

这类项必须保留为不同测试点。

## PT081 当前已知问题映射

对 PT081 而言，以下问题已确认属于低信号膨胀：

- 主用例中大量“基础属性与控件定义一致”类 testcase
- 创建人 / 创建时间 / 修改时间等元数据类 testcase
- 同一目标字段、同一断言结果在 `explicit_rule` 与 `ai_reasoning` 两侧重复生成

以下问题已确认必须由主链承接：

- `5s自动轮播`
- `每tab最多5条 / 4条 / 3条`
- `默认关闭`
- `顶部tab归属`
- 条件展示 / 条件必填 / 条件编辑性
- 数据源过滤 / 排序

## 必填 / 必选默认口径

- 只有需求文字明确出现“必填 / 必选 / 不能为空 / 必须填写 / 必须选择 / 必传”等强制语义，或原型图字段旁出现必填星号 `*` / 等价标识时，才生成“为空保存失败 / 阻止提交 / 不可提交”类用例。
- 若需求和原型均未说明必填，则字段默认非必填。单选、多选、筛选项、下拉框、枚举字段本身不构成必填证据。
- 默认非必填字段仍可生成展示、候选项、筛选效果、默认不选展示全部、可选配置等用例，但不得脑补必填拦截。

## 使用方式

从 Phase 1 开始，所有新增的 `coverage_level`、`emit_mode`、去重策略、主用例 / audit 分流与质量门口径，都必须以本文件为准。
