## 2. 需求结论

在 MySQL 上，当字段同时存在 `db_index=True` 生成的普通索引和 `Meta.constraints` 中同列的命名 `UniqueConstraint` 时，后续只移除 `db_index=True` 不得删除未变化的唯一约束。迁移后普通索引应被移除，命名唯一约束及其数据库唯一索引必须继续存在并强制唯一性。

## 3. 前置条件 / 准备工作

- 使用支持该行为复现的 Django 版本与 MySQL 8.4。
- 模型字段初始设置 `db_index=True`。
- 同一字段在 `Meta.constraints` 中声明命名 `UniqueConstraint`。
- 初始迁移已应用，数据库同时存在普通索引与唯一索引。

## 4. 业务范围与不做范围

范围内：删除字段 `db_index` 属性生成的迁移、普通索引删除、未变化唯一约束保留、迁移后数据库唯一性。

范围外：新增或删除 `UniqueConstraint` 本身；其他数据库后端的内部实现；外键支撑索引；未在来源中说明的复合字段或条件唯一约束行为。

## 5. 面向研发的需求拆解

- 迁移差异只包含从字段移除 `db_index=True`。
- 定位待删除普通索引时，必须排除 `Meta.constraints` 中仍存在的命名约束。
- 执行迁移后，不再保留字段普通非唯一索引。
- 执行迁移后，命名唯一约束仍存在，数据库继续拒绝重复值。

## 6. 面向测试的验收关注点

- 初始状态可明确识别同列的普通索引和命名唯一索引。
- 生成的迁移 SQL 只删除普通索引，不包含删除命名唯一约束的语句。
- 应用迁移后命名唯一约束仍可被数据库 introspection 识别。
- 应用迁移后写入重复字段值仍被数据库拒绝。
- 迁移前已有合法数据保持不变。

## 7. 数据 / 埋点 / 接口 / 配置要求

- 示例字段：`username`。
- 示例约束名：`unique_username`。
- 数据库：MySQL 8.4。
- 来源未声明 API、埋点或运行时配置变更。

## 8. 风险与兼容性

- MySQL 将唯一约束表现为唯一索引，可能导致普通索引查找误命中约束索引。
- 不同 Django 维护版本的迁移行为需要分别确认；来源只报告 6.1 和 4.2。
- 迁移 SQL 正确不等于最终数据库状态正确，需要同时验证 schema 和重复写入行为。
