# CELERY-10668 跨 Worker 时钟域保留撤销任务需求整理

整理时间：2026-09-21

## 1. 资料来源

- `primary_requirement`：Celery PR #10668 的公开问题描述与行为目标。
- `context_only`：PR 中记录的 Celery 5.6.3、Kubernetes、高频撤销和集合容量现象，仅用于复现背景。
- 本地冻结快照：`inputs/public_source_snapshot.md`。
- 代码 diff 与 PR 中列出的测试实现被隔离为后续 Oracle，本阶段未消费。

## 2. 需求结论

Worker 从其他主机或持久化状态接收已撤销任务时，不得直接复用来源主机的 monotonic 时间戳。接收的任务 ID 应在本机时钟域重新建立有效期，避免外部时间戳长期占满撤销集合并驱逐本机新撤销任务。被撤销的 ETA/countdown 任务在有效期内不得执行。

## 3. 前置条件 / 准备工作

- 至少两个启动时长不同的 Worker，启用启动同步。
- 准备带 ETA/countdown 的任务和可观察的任务执行副作用。
- 可配置撤销集合 `maxlen` 与 `REVOKE_EXPIRES`。
- 准备 `--statedb` 持久化并模拟主机重启后的恢复。

## 4. 业务范围与不做范围

范围内：`hello`/mingle 撤销状态交换、`--statedb` 恢复、本机新撤销任务保留、撤销过期、滚动升级兼容和同时间戳条目稳定排序。

范围外：一般任务路由、正常任务执行语义、未声明的远程控制协议变更，以及与撤销无关的 worker 状态。

## 5. 面向研发的需求拆解

- 外部撤销状态只以任务 ID 参与合并，不把外部 monotonic 时间戳作为本机有效期依据。
- 接收的任务 ID 从本机收到时开始计算撤销有效期。
- 集合达到容量时，本机刚撤销的任务不得被错误驱逐。
- `hello`、mingle 和 `--statedb` 三条入口保持一致语义。
- 新旧 Worker 混合集群应能兼容两种撤销状态表示。
- 同一时刻加入不同类型任务 ID 时不得因比较 ID 类型产生错误。

## 6. 面向测试的验收关注点

- 来源 Worker 时间戳明显领先时，接收 Worker 仍按本机时间处理撤销状态。
- 集合满载后新增本机撤销任务仍保留，被撤销 ETA 任务不会执行。
- 收到的撤销 ID 在配置有效期内有效，并可在有效期后正常过期。
- `hello`、mingle 与 `--statedb` 恢复分别验证。
- 新旧版本双向交换撤销状态时不丢失撤销 ID。
- `now=0`、相同时间戳及 int/string 混合 ID 不触发排序或比较异常。

## 7. 数据 / 埋点 / 接口 / 配置要求

- 关键状态：revoked task ID 集合、接收时间、过期时间、集合容量。
- 关键配置：`CELERY_WORKER_REVOKE_EXPIRES` / `REVOKE_EXPIRES`、`maxlen`、`--statedb`。
- 可观察结果：任务未执行、撤销 ID 是否存在及是否按期过期、Worker 是否异常。

## 8. 风险与兼容性

- 滚动升级期间旧 Worker 与新 Worker 的状态格式兼容是核心风险。
- 重新从接收时间计算有效期会延长部分撤销 ID 的存活时间，但优先保证不错误执行任务。
- 高频撤销和满容量条件下才容易暴露驱逐问题，普通小样本可能产生假通过。
- 跨主机 monotonic 时钟不可比较，测试不能用墙钟调整替代真实时钟域差异。
