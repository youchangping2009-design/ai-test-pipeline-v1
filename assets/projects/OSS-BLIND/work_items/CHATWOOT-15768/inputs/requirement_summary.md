# CHATWOOT-15768 Conversation filter typed value matching 需求整理

整理时间：2026-09-21

## 1. 资料来源

- Chatwoot GitHub PR #15768，状态为已合并，目标分支为 `develop`。
- 公开关联问题 #15767，用于理解客户端二次过滤造成的计数与列表不一致背景。
- 本地冻结快照：`inputs/public_source_snapshot.md`。
- 为保持盲测，代码 diff 与新增测试不作为需求输入。

## 2. 需求结论

会话高级筛选必须按自定义属性的真实数据类型生成并匹配筛选值。数字属性应产生数字输入；数值 `{0}` 与布尔值 `{false}` 是有效值，不得被当成空值。客户端会话匹配继续使用严格相等，不应把所有属性统一转换为字符串。

## 3. 前置条件 / 准备工作

- 创建数字型、checkbox/布尔型自定义会话属性。
- 准备属性值分别为正数、`0`、`true`、`false`、空值和缺失字段的会话。
- 可从会话列表打开高级筛选，并观察筛选后的列表及数量。
- 若验证关联问题背景，应分别从具体 inbox 与 All Conversations 进入筛选。

## 4. 业务范围与不做范围

范围内：数字输入和值转换；`0`、`false` 在查询、校验和客户端匹配链路中的保留；`equal_to` 与 `not_equal_to`；缺失属性与显式 falsy 值的区分。

范围外：不迁移历史字符串型筛选值；不把所有属性转换为字符串；inbox ID 原始类型修复属于另一个 PR；不修改后端 SQL 过滤语义。

## 5. 面向研发的需求拆解

- number 自定义属性的筛选控件和值转换必须保持数值类型。
- 生成请求时只把 `null`、`undefined`、空字符串等真正空值视为空；`0` 和 `false` 必须保留。
- 读取 conversation custom attribute 时不得依赖 truthy 判断。
- 客户端匹配保持严格相等，输入和值的数据类型应在链路前端正确归一。

## 6. 面向测试的验收关注点

- 数字属性输入正数和 `{0}` 后，请求及本地匹配均保留 number 类型。
- checkbox 属性为 `{false}` 时仍能被 `equal_to` 命中，并被 `not_equal_to` 排除。
- 属性缺失时不得与 `{0}` 或 `{false}` 混淆。
- `null`、`undefined`、空字符串、空数组、空对象的校验差异按既有规则验证，不自行假设全部等价。
- 数量徽标和会话列表结果应一致；若不一致，应区分后端结果与客户端二次过滤。
- 文本、日期、列表等既有筛选类型不得回退。

## 7. 数据 / 埋点 / 接口 / 配置要求

- 核心数据：custom attribute 定义类型、conversation 实际值、filter payload 的 values。
- 关键运算符：`equal_to`、`not_equal_to`。
- 关联接口背景：`POST /api/v1/accounts/:id/conversations/filter`。
- PR 未声明新增接口字段、数据库迁移或埋点。

## 8. 风险与兼容性

- 历史保存的字符串数字筛选不会自动迁移，可能继续与数字属性严格匹配失败。
- JavaScript falsy 语义可能同时影响校验、请求生成和本地列表过滤，需要跨层一致性验证。
- inbox ID 类型问题与本次修复共享匹配路径，但属于独立变更。
