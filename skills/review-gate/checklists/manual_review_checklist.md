# Manual Review Checklist

用于人工评审以下产物：

- evidence_inventory
- 结构化 PRD
- traceability_matrix
- 测试用例
- Flow 流程定义
- 输出格式与规则符合性
- 前端代码 CR / 后端代码 CR / 人工确认

---

## 零、Evidence / Traceability 评审

### 1. Evidence Inventory

- [ ] 是否沉淀了关键截图证据
- [ ] 图上可见入口是否没有静默丢失
- [ ] 无法确认的证据是否标记为 `needs_confirmation`

### 1.1 Image Evidence Inventory

- [ ] 图片类输入是否优先沉淀为 `image_evidence_inventory.json`
- [ ] 列表区是否提取了列头和操作列
- [ ] 添加/编辑弹窗是否提取了字段矩阵
- [ ] 字段是否补充了 `control_type / required / editable / default_value / data_source`
- [ ] 红字注释中的固定 content、条件展示、条件不可编辑是否没有静默丢失
- [ ] 说明表是否逐行提取
- [ ] 删除限制、引用关系、精确提示语是否被结构化承接

### 1.2 图片型后台配置页黄金样板

- [ ] 是否按 `filter_area / list_area / action_area / edit_modal / sort_modal / field_rule_table` 还原页面骨架
- [ ] 列表区是否承接了列头字段、元数据列和操作列
- [ ] 操作区是否承接了 `添加 / 编辑 / 复用 / 删除 / 排序`
- [ ] 添加/编辑弹窗是否保留字段级属性：类型、必填、默认值、来源、可编辑性
- [ ] 条数上限、默认值、删除限制、状态原词是否原样进入中间产物
- [ ] `banner / 瓷片区 / 金刚区 / 弹窗` 家族差异是否已命中：`5 / 4 / 4 / 3` 条上限、`展示企微单人单码`、`展示规则`

### 2. Traceability Matrix

- [ ] evidence 是否都映射到 structured item
- [ ] 可测试 evidence 是否映射到 testcase
- [ ] 是否能定位“图上有但结构化漏了”的问题
- [ ] 是否能定位“结构化有但 testcase 漏了”的问题

---

## 一、结构化 PRD 评审

### 1. 基础结构完整性

- [ ] 是否包含 `project_info`
- [ ] 是否包含 `requirement_info`
- [ ] 是否包含 `modules`
- [ ] 是否包含 `flows`
- [ ] JSON 是否可读、无明显结构错误
- [ ] 顶层字段命名是否符合英文 snake_case 规范

---

### 2. project_info 评审

- [ ] `project_code` 是否存在且合理
- [ ] `project_name` 是否存在
- [ ] `business_line` 是否合理
- [ ] `prd_source` 是否可追溯
- [ ] `prd_version` 是否合理
- [ ] 缺失信息是否明确标记为“待确认”

---

### 3. requirement_info 评审

- [ ] `requirement_title` 是否明确
- [ ] `requirement_background` 是否符合原始 PRD 语义
- [ ] `requirement_goal` 是否明确
- [ ] `explicit_rules` 是否提取了前置说明、功能说明和补充文档中的高优先级规则
- [ ] `explicit_rules` 中的精确约束是否被抽象成通用约束类型，并保留了原始值
- [ ] 固定文案、样式差异、容器结果、默认状态、扩展性说明是否进入 `explicit_rules` 或可追溯结构
- [ ] `scope.in_scope` 是否合理
- [ ] `scope.out_of_scope` 是否合理
- [ ] 是否存在明显遗漏的需求范围信息

---

### 4. modules / features / rules 评审

- [ ] 模块拆分是否符合业务语义
- [ ] 是否存在明显应拆未拆的模块
- [ ] feature 是否足够原子化
- [ ] rules 是否为原子规则
- [ ] 是否存在将多个规则粗暴合并的情况
- [ ] 是否存在模糊规则描述（如“功能正常”“支持配置”等）
- [ ] 是否遗漏关键业务规则
- [ ] 是否把组合型说明正确拆成了展示 / 交互 / 数据 / 状态或补齐规则，而不是只保留摘要
- [ ] 是否把“触发动作 -> 容器出现 -> 默认状态 / 终态结果”拆成多个可验证检查点
- [ ] 是否保留固定文案、特殊样式、容器名称、默认选中、扩展性说明等非数据类规则
- [ ] entry_conditions 是否合理
- [ ] dependencies 是否合理

---

### 5. field_definitions 评审

- [ ] 字段是否尽量完整提取
- [ ] `field_name` 是否为英文 snake_case
- [ ] `display_name` 是否与 PRD 展示语义一致
- [ ] `data_type` 是否合理
- [ ] `required` 是否合理
- [ ] `enum_values` 是否完整
- [ ] `format_rule` 是否合理
- [ ] `length_rule` 是否合理
- [ ] `data_source` 是否明确
- [ ] `terminal` 是否明确
- [ ] 是否遗漏关键字段
- [ ] 是否遗漏关键字段规则
- [ ] 是否补充了 `field_rules`
- [ ] 是否补充了 `field_rule_tables`
- [ ] 若存在字段说明表，是否已正确绑定到对应字段
- [ ] 若说明表没有独立交互，是否避免把它建成独立业务对象
- [ ] 状态字段的 `enum_values` 是否原词保留
- [ ] 字段的 `editable / default_value / data_source / conditional_visibility / conditional_editability` 是否在有依据时尽量补齐

---

### 6. 异常 / 边界场景评审

- [ ] `abnormal_scenarios` 是否合理
- [ ] `boundary_scenarios` 是否合理
- [ ] 是否覆盖空值 / 极值 / 非法输入 / 状态异常
- [ ] 是否存在补充不足的问题
- [ ] 是否存在明显脱离业务的过度补充

---

## 二、Flow 结构评审（新增重点）

### 1. Flow 基础完整性

- [ ] 是否存在 `flows`
- [ ] 是否至少存在 1 个有效 `main_flow`（有连续业务链路时）
- [ ] `flow_id` 是否唯一
- [ ] `flow_name` 是否能明确表达业务链路
- [ ] `flow_type` 是否合法
- [ ] `business_goal` 是否明确
- [ ] `steps` 是否非空
- [ ] `main_flow` 是否包含 `success_criteria`
- [ ] `main_flow` 是否包含 `priority`
- [ ] `main_flow` 是否包含 `tags`

---

### 2. Flow 提取合理性

- [ ] Flow 是否描述了关键业务链路，而不是字段规则集合
- [ ] Flow step 是否是业务动作粒度，而不是 UI 点击粒度
- [ ] 是否存在应抽取但未抽取的关键主流程
- [ ] 是否遗漏跨模块关键链路
- [ ] 是否遗漏审核 / 发布 / 生效 / 回传类链路
- [ ] Flow 是否与需求目标一致

---

### 3. Flow 与 modules 的映射关系

- [ ] 每个 step 的 `module_name` 是否存在于 `modules` 中
- [ ] 每个 step 的 `feature_name` 是否存在于对应 module 中
- [ ] `related_modules` 是否与 steps 中实际使用模块一致
- [ ] 是否存在悬空 Flow
- [ ] 是否存在 Flow 脱离 PRD 结构的情况

---

### 4. Flow steps 评审

- [ ] `step_no` 是否从 1 连续递增
- [ ] `step_name` 是否为清晰业务动作
- [ ] `action` 是否明确可理解
- [ ] `expected_result` 是否明确可验证
- [ ] `step_type` 是否合理
- [ ] `actor` 是否合理
- [ ] `input_data` 是否有助于后续测试设计
- [ ] `state_transition` 是否合理
- [ ] `rule_references` 是否与原子规则对应
- [ ] `is_key_checkpoint` 标记是否合理

---

### 5. Checkpoints / Success Criteria 评审

- [ ] 关键步骤是否定义了 `checkpoints`
- [ ] `is_key_checkpoint=true` 时，是否确实存在 checkpoint
- [ ] checkpoint 是否覆盖：
- [ ] 页面结果
- [ ] 接口结果
- [ ] 状态变化
- [ ] 数据落库
- [ ] 下游可见性
- [ ] 生效结果
- [ ] `success_criteria` 是否可验证
- [ ] `success_criteria` 是否体现流程成功的终态

---

## 三、测试用例评审

### 1. 基础输出质量

- [ ] 是否为标准 Markdown 表格
- [ ] 表头是否正确
- [ ] 每行是否表示 1 条独立用例
- [ ] 是否存在空列 / 空值明显缺失
- [ ] 是否存在大量重复用例
- [ ] 是否存在明显无意义用例

---

### 2. 单点用例评审

- [ ] 是否覆盖主要 modules
- [ ] 是否覆盖主要 features
- [ ] 是否覆盖 rules
- [ ] 是否覆盖 field_definitions
- [ ] 是否覆盖异常场景
- [ ] 是否覆盖边界场景
- [ ] 是否覆盖权限场景
- [ ] 是否覆盖数据校验场景
- [ ] 高优先级 `explicit_rules` 是否都有对应 testcase 承接
- [ ] testcase 是否保留了精确约束的原始值，而不是改写成泛化表述
- [ ] testcase 是否覆盖固定文案、样式差异、容器结果、默认状态等 UI 侧精确约束
- [ ] 组合规则是否覆盖触发动作、目标容器、默认状态和容器内结果，而不是只覆盖终态
- [ ] 每个页面模块是否完成展示 / 交互 / 数据规则 / 状态接口四层评估
- [ ] 页面展示类需求是否同步评估了 AI-API 候选，而不是只生成 AI-UI 用例
- [ ] 同一验证点若同时存在 AI-API / AI-UI，用例是否明确主辅关系
- [ ] 备注中是否能看出主验证层与关联验证点
- [ ] 是否存在“验证功能正常”这类泛化标题
- [ ] 预期结果是否具体可验证

### 2.1 后台配置页专项拦截项

- [ ] 是否遗漏列表区列头承接
- [ ] 是否遗漏字段级属性承接：可编辑、数据来源、字段类型、必填、默认值
- [ ] 是否遗漏说明区中的限制规则：条数上限、删除限制、引用限制、默认值
- [ ] 是否遗漏条件字段与联动字段，如 `选择活动 / 展示规则 / 条件不可编辑`
- [ ] 每个后台配置页是否至少覆盖了 `添加弹窗 / 列表区 / 操作区 / 排序弹窗`
- [ ] `edit_modal` 是否至少拆成了“字段矩阵完整性”和“条件联动”两类承接，而不是只保留一条摘要型用例

---

### 3. 流程型用例评审（新增重点）

- [ ] 是否为每个 main_flow 生成至少 1 条完整流程型用例
- [ ] pre_flow / post_flow / support_flow 是否按需生成流程型用例
- [ ] 流程型用例标题是否体现完整业务目标
- [ ] 流程型用例是否覆盖关键步骤
- [ ] 是否覆盖关键 checkpoint
- [ ] 是否覆盖 success_criteria
- [ ] 是否体现状态流转
- [ ] 是否体现最终业务结果
- [ ] 是否只是简单拼接 step，缺少关键验证
- [ ] 是否遗漏流程终态校验

---

### 4. 步骤与预期结果质量

- [ ] 测试步骤是否可执行
- [ ] 测试步骤是否避免 UI 点击流水账
- [ ] 预期结果是否可检查
- [ ] 预期结果是否避免“正常/成功/符合预期”这类模糊表达
- [ ] 单点用例是否清晰表达验证点
- [ ] 流程型用例是否体现链路闭环
- [ ] 页面 / Tab 是否使用 `[]` 标注
- [ ] 按钮 / 操作入口是否使用 `【】` 标注
- [ ] 弹窗 / 抽屉 / 面板是否使用 `《》` 标注
- [ ] 字段 / 表单项 / 列表列是否使用 `“”` 标注
- [ ] 枚举值 / 输入值是否使用 `{}` 标注
- [ ] 状态 / 标签 / 结果是否使用 `<>` 标注
- [ ] 提示语 / Toast / 校验文案是否使用 `「」` 标注
- [ ] 接口 / 参数 / 技术字段是否使用反引号标注
- [ ] 是否存在弹窗和字段都用 `“”` 的符号误用
- [ ] 是否存在对普通动词、泛化名词的过度标注

---

### 5. 编号 / 标签 / 优先级评审

- [ ] 用例编号是否唯一
- [ ] 编号格式是否符合规则
- [ ] Flow 用例是否使用合适的 type_code（如 FL / ST / DV）
- [ ] 标签是否只使用封闭集合
- [ ] 标签中是否错误承接页面 / 页面模块 / 终端 / 测试类型信息
- [ ] 每条用例是否至少包含 1 个自动化执行载体或人工执行责任标签
- [ ] 核心流程或关键变更是否同时包含 `开发必测` 与 `测试必测`
- [ ] 流程型用例是否通过测试类型、备注和编号 type_code 识别，而不是依赖旧标签
- [ ] 高风险 main_flow 用例是否按需使用“核心链路”/“黄金用例”/“评审用例”等合法标签
- [ ] 优先级是否合理
- [ ] main_flow 是否默认高优先级

---

### 6. 用例组织方式评审

- [ ] 是否为需要代码映证的用例补充了代码映证类型标记
- [ ] 是否区分了 `frontend_behavior / backend_contract / shared_contract / prd_only`
- [ ] 是否标记了建议执行的 CR 阶段：前端 CR / 后端 CR / 双 CR / 无需 CR
- [ ] 是否标记了是否需要人工确认

## 四、代码评审阶段评审

### 1. 前端代码 CR

- [ ] 是否聚焦前端可直接映证的行为：点击能力、显隐状态、文案、样式差异、容器结果、计时器、前端排序/过滤/补齐
- [ ] 是否识别了“PRD 有、用例有，但当前前端代码未落地”的项
- [ ] 是否识别了“用例要求存在，但当前前端代码没有点击能力/没有入口/没有状态”的无效项
- [ ] 前端 CR 是否未修改业务代码
- [ ] 前端 CR 是否未修改历史产出物
- [ ] `frontend_confirmation.json` 是否已人工确认

### 2. 后端代码 CR

- [ ] 是否聚焦后端可直接映证的行为：数据来源、状态过滤、排序主次规则、分页、默认值、补齐逻辑、字段契约
- [ ] 是否识别了“前端无法证明、必须在后端 CR 才能关闭”的点
- [ ] 是否识别了“用例要求为后端契约，但当前仅停留在 PRD 或共享契约”的项
- [ ] 后端 CR 是否未修改业务代码
- [ ] 后端 CR 是否未修改历史产出物
- [ ] `backend_confirmation.json` 是否已人工确认

## 五、输出格式与规则符合性
- [ ] 用例是否按“页面 → 板块 → 页面模块 → 功能点”视角组织
- [ ] 页面归属是否清晰
- [ ] 板块归属是否清晰
- [ ] 页面模块归属是否清晰

- [ ] 是否仍然输出成单一总表，而不是按页面 / 板块分组
- [ ] 每个 `field_rules` 是否至少被 1 条 testcase 承接
- [ ] 每个 `field_rule_tables` 是否至少被 1 组 testcase 承接

- [ ] 状态字段枚举值是否在 testcase 中原词保留
