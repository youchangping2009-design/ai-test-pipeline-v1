# Numbering And Tagging Skill

## 目标

为测试用例统一应用：

- 编号规则
- 标签规则
- 优先级规则

该技能为 `Case Generator` 与 `Case Reviewer` 提供基础约束。

---

## 输入

输入通常包括：

- 已生成的 testcase 行
- 所属项目编码
- 所属模块 / 功能点
- 用例类型
- 是否为流程类用例
- 是否涉及状态流转 / 数据校验 / 核心链路 / 高风险评审

---

## 输出

对 testcase 的以下字段进行标准化：

- `用例编号`
- `标签`
- `优先级`
- `测试类型`

## 执行步骤

### 1. 应用编号规则

默认格式：

`{project_code}-{page_code}-{page_module_code}-{terminal_code}-{type_code}-{seq}`

必须保证：

- 编号唯一
- 不重复
- 不混乱复用
- page_code / page_module_code / terminal_code / type_code 不缺失
- 流程型用例也必须按主入口页面与主控制模块归档

---

### 2. 应用标签规则

标签分为四类语义：

- 自动化执行载体：
  - `AI-API用例`
  - `AI-UI用例`
- 人工执行责任：
  - `测试必测`
  - `开发必测`
- 风险标识：
  - `黄金用例`
  - `核心链路`
- 评审投入：
  - `评审用例`

每条用例至少应包含 1 个自动化执行载体或人工执行责任标签：

- `AI-API用例`
- `AI-UI用例`
- `测试必测`
- `开发必测`

打标时必须先判断适合沉淀的执行载体：

- 能通过 API / 数据 / 服务端断言稳定覆盖时，优先打 `AI-API用例`
- 需要页面渲染、交互、弹窗、视觉状态时，打 `AI-UI用例`
- API 与 UI 都有价值时，两个载体标签可以同时存在
- 非核心且可被 AI-API / AI-UI 稳定覆盖的用例，可以不追加 `测试必测` 或 `开发必测`

核心流程或关键变更用例必须包含：

- `开发必测`
- `测试必测`

开发必测优先用于：

- 接口规则
- 数据源过滤 / 排序
- 指标计算
- 状态流转
- 保存前后端校验
- 低成本可自测的配置落库规则

流程类用例应重点考虑：

- `黄金用例`
- `核心链路`
- `评审用例`

禁止作为标签：

- 页面名称
- 页面模块名称
- 终端
- 测试类型

---

### 3. 应用优先级规则

普通原则：

- P0：核心链路、资金 / 数据 / 发布高风险
- P1：重要功能与重要支撑
- P2：一般功能
- P3：低风险弱影响项

Flow 优先级重点原则：

- `main_flow` 默认 P0
- `pre_flow / post_flow` 默认 P1，必要时升 P0
- `support_flow` 默认 P1 / P2

---

## 流程型用例特殊约束

流程类用例在应用规则时必须额外检查：

- 测试类型是否为 `流程验证 / 状态流转 / 数据校验`
- 编号 type_code 是否为 `FL / ST / DV`
- 若为黄金用例 / 核心链路，优先级是否为 P0
- 是否至少命中 1 个自动化执行载体或人工执行责任标签
- 核心流程是否同时包含 `开发必测` 与 `测试必测`

---

## 自检清单

输出前必须自检：

- 编号是否唯一
- type_code 是否匹配真实验证目标
- 标签是否只使用封闭集合
- 流程型用例是否通过测试类型 / 备注 / 编号识别
- 优先级是否与业务风险匹配

---

## 禁止行为

禁止：

- 随意手写自由格式编号
- 忽略流程型用例特殊类型码
- 用“功能”替代所有流程型用例测试类型
- 对黄金流程打低优先级
- 用页面 / 终端 / 测试类型充当标签
